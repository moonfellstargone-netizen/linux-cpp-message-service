# 源码阅读与理解验收

本项目由 AI 辅助实现。代码可以编译或测试通过，与用户本人能够独立修改和排障，是两项不同的验收。下面的练习尚待用户完成。

## 阅读顺序

1. `include/msg/protocol.hpp`：先看长度常量、`decode_length`、`frame`、`parse_frame`、`make_response`。用 `hi` 手算头部及响应，解释长度为什么按字节而不是字符计算。
2. `include/msg/unique_fd.hpp`：解释文件描述符由谁持有，析构何时关闭，为什么禁止复制、允许移动，`release` 与 `reset` 分别做什么。
3. `src/server.cpp`：按监听、接受连接、维护每连接缓冲、等待就绪、接收、解析、排队响应、发送、清理的顺序画一张自己的流程草图。先解释一条正常请求，再看错误分支。
4. `src/client.cpp`：跟随一行输入到完整回复，找出部分发送、部分接收、EOF 和错误处理的位置。
5. `tests/protocol_test.cpp` 与 `tests/integration_test.py`：把每项用例对应到一个协议规则或资源清理路径，区分已实际覆盖的行为和仍未验证的状态。

不得因还不熟悉某个分支就删掉它以“简化”项目。

## 先能独立回答

- 如果先收到 2 字节头，下次又收到剩余头与一半正文，程序当前保留什么状态？
- 两条请求同时到达，为什么不会被当成一条？正文中出现 NUL 或换行会怎样？
- 长度头声明 4 GiB 左右的数据时，为什么不会分配相应的大缓冲？
- `send` 只发送部分数据，或者返回 `EAGAIN`，下次从哪里继续？
- 为什么只有存在待发送数据时才应该等待可写事件？
- 客户端半关闭发送方向、直接关闭连接、进程被终止，在程序观察到的结果上有什么差异？
- 一条连接解析失败时，哪些对象和描述符应被清理，其他连接的状态为什么仍保留？

可以看文档学习，验收时先独立解释，再对照源码核对。不要求背诵系统调用参数。

## 小修改：调整请求长度上限

在可恢复的版本基础上，把请求上限从 1024 改为 512 字节。先独立尝试，不直接让 AI 给出补丁。

1. 找出受影响的常量、响应上限、客户端输入检查、测试和文档。
2. 写下 511、512、513 字节的预期行为，另确认 UTF-8 输入仍按字节计算。
3. 修改后重新构建和测试；在真实 socket 上验证最大合法请求能得到回复，超限请求被拒绝，并检查其他正常连接不受影响。
4. 解释为什么只改 README、只改客户端或只改服务端都不够。记录实际修改位置、失败输出与修正过程。

目标是让行为与协议一致，不是让旧测试被删除后变成绿色。完成后可恢复原上限，或者保留修改并同步协议与测试，二者任选其一但应记录。

## 小排障：收到一半时断开

在运行前预测服务端如何处理“只发两个头字节就断开”，再用测试复现。指出 EOF、残帧识别、日志及释放连接的对应位置，并检查另一个连接仍可用。

练习完成的证据包括自己的解释、修改、运行结果和一次真实问题记录。尚未完成时，求职表述应保留“AI 辅助实现，正在验证与复盘”，不能称为已经独立掌握。
