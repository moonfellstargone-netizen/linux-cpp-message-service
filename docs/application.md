## 面试准备：先解释证据，再谈掌握程度

下面是核对源码用的简短答案，不是已经完成的个人能力验收。应先自行解释，再用源码、测试和原始记录核对。

1. **为什么不能把一次 `recv` 当作一条消息？**
   TCP 提供字节流；接收结果可能不足一帧，也可能包含多帧。项目先收集 4 字节长度，再等待指定长度的正文；数据不足时保留，完整后循环解析，0 或超长长度被拒绝。依据：[协议实现](../include/msg/protocol.hpp)、[拆分与连续帧单元测试](../tests/protocol_test.cpp)、[连接测试](../tests/integration_test.py) 的 `test_fragmented_header_and_body` 和 `test_coalesced_frames`。

2. **单线程为什么能同时处理多个连接，为什么选择 `poll`？**
   socket 设置为非阻塞，`poll` 等待就绪事件，各连接分别保存状态；一条连接暂时不能推进时，循环还能处理其他连接。本版选择便于理解的小规模路线，没有测量证明 `poll` 优于其他模型，64 条上限也不是吞吐结论。依据：[服务端事件循环](../src/server.cpp)、[连接上限与隔离测试结果](../reports/ci-58fb118/debug/integration.json)。

3. **`send` 只发出一部分时怎样继续？**
   保存当前队首响应的发送偏移，成功发送多少就扣减多少待发送字节；`EAGAIN` 保留状态等待可写，`EINTR` 重试，永久错误清理对应连接。待发送数据不为空时才关注可写事件。依据：[服务端 `send_replies` 与事件订阅](../src/server.cpp)。慢接收端测试验证了保护及其他连接可用，但没有证明所有部分发送分支实际执行，见 [测试报告的限制](../reports/ci-58fb118/debug/integration.json)。

4. **接收 EOF 就立即关闭吗？**
   残帧遇到 EOF 按不完整消息清理；完整请求后半关闭发送方向时，服务端先排空已排队回复，再关闭。普通断连、重置和错误不保证回复能够到达。依据：[服务端 EOF 路径](../src/server.cpp)、[连接测试](../tests/integration_test.py) 的 `test_incomplete_orderly_eof`、`test_incomplete_reset`、`test_half_close_complete_frame`。

5. **怎样管理描述符，怎样解释资源检查？**
   `UniqueFd` 持有描述符，禁止复制、允许移动，析构或 `reset` 时关闭；连接移除后其缓冲也随对象释放。50 次顺序连接后 FD 从 4 回到 4，只说明本次场景未观察到描述符持续增长，不能证明无内存泄漏。64 连接和缓冲上限用于保护资源。依据：[描述符所有权](../include/msg/unique_fd.hpp)、[服务端连接清理](../src/server.cpp)、[实测报告](../reports/ci-58fb118/debug/integration.json)。

6. **已经有 `MSG_NOSIGNAL`，为什么服务端仍出现 SIGPIPE？**
   它只作用于对应 socket 的发送。实际故障由 `std::cerr` 写入已经失去读取端的日志管道触发，进程退出状态为 `-13`。修复将进程的 `SIGPIPE` 处理设为忽略，回归确认仍可请求回复；不会恢复已关闭的日志目标，也不保证日志永不阻塞。依据：[修复前原始结果](../reports/ci-ed70dad/debug/integration.json)、[修复后结果](../reports/ci-58fb118/debug/integration.json)、[完整排障记录](debugging.md)。

7. **为什么输入读取错误不能只检查 `eof()`？**
   在本项目默认 stdio 同步方式下，目录描述符的底层读取失败可能在 iostream 路径呈现为 EOF。项目额外检查 `std::ferror(stdin)`，将其报告为输入错误并非零退出；正常 EOF 尾行仍按独立规则处理。依据：[客户端有界读取与错误检查](../src/client.cpp)、[目录输入回归](../tests/integration_test.py) 的 `test_client_stdin_read_error`、[修复前后记录](debugging.md)。

8. **20 项测试和 ASan/UBSan 通过，能证明什么？**
   只证明对应提交在记录的 Ubuntu CI 条件下通过这些用例，不能证明不存在所有缺陷。用例含 3 客户端收发、50 次顺序连接、64 连接上限、非法帧、半关闭和输入错误等；这些不是百万连接或生产负载。sanitizer 检查也受执行路径限制，测试清理还需检查退出码。依据：[普通报告](../reports/ci-58fb118/debug/integration.json)、[ASan/UBSan 报告](../reports/ci-58fb118/asan-ubsan/integration.json)、[构建环境](../reports/ci-58fb118/debug/environment.txt) 与 [测试清理排障](debugging.md)。
